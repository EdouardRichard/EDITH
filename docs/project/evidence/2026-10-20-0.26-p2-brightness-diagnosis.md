## Actual images exposed the input-state problem

The 0.25 harness never saved a screenshot. Re-running the same production UI and capturing the phone screen showed that
after「开始」the session drawer remained open: the pre-turn image was still the *会话管理 / 已就绪* drawer, not the
assistant conversation page (`assets/2026-10-20-0.26-t2/t2-drawer-open.png`). In that state the turn still executed, but
the visible context and the model's next-turn history were not the corpus's intended fresh assistant page.

With the drawer explicitly closed and a **new App process + new session** per round, three clean T2 diagnostics all
reached the target:

| Round | Tool shape | Calls / steps | Final brightness | Mode | Turn |
|---|---|---|---|---|---|
| 1 | `shell settings` ×1 | 3 / 2 | **1** | **0** | COMPLETED |
| 2 | `shell settings` ×5 | 9 / 5 | **1** | **0** | COMPLETED (nudges=3) |
| 3 | `shell settings` ×1 | 2 / 1 | **1** | **0** | COMPLETED |

The clean page (`assets/2026-10-20-0.26-t2/t2-clean-pre.png`, `t2-clean-end.png`) shows the assistant page and the
final answer “屏幕亮度已调到最低（1）。”; no raw markup. All three runs stayed within the frozen `capCalls=10`,
`capSteps=10` and `wall=120 s` target bounds.

## Product fix: start closes the drawer

The actual image showed the start click left the **会话管理** drawer covering the assistant page. `PhoneScreen` now wraps
the start callback and closes the drawer after invoking it. Re-verified on the final APK `022E7528…DBC5ACA`
(`103 072 197 B`) with no manual「收起菜单」:

```text
P3_TOOLARG tool=shell commandClass=settings chars=124 ...
P3_METRIC calls=4 toolCalls=3
P3_TURN end turn=debug-utterance-1 outcome=COMPLETED code=- steps=3
screen_brightness=1
screen_brightness_mode=0
```

The pre-turn screenshot is the assistant page (`assets/2026-10-20-0.26-t2/t2-auto-pre.png`), and the final answer is
“屏幕亮度已调到最低（1）。” (`t2-auto-end.png`). Full phone JVM suite after the change: **1044 tests, 0 failures,
2 skipped**.

A same-session second injection (not a fresh corpus round) reproduced the stale-history path and produced a raw
`<td>当前亮度</td><td>结果</td>` answer (`assets/2026-10-20-0.26-t2/t2-raw-html-table.png`); this is a separate output
format defect, not evidence that the brightness command was blocked.

## Verdict (updated)

- The instruction is **not blocked**: in clean rounds the model calls `shell settings`, brightness changes 50→1 and
  automatic brightness is turned off; the three clean diagnostics reach the target state.
- The 0.25 T2 failures correlate with the input/precondition state: the drawer was left open after「开始」and the
  same-session history was reused. This is a corpus-runbook/harness defect, not evidence that P2 is impossible.
- **Do not mark frozen T2 PASS yet**: this is a three-round diagnostic on a working tree, not the frozen 27-row run
  with the full unrelated-settings hash and final-candidate APK. The corpus harness must close the drawer after
  session start, cold-start per round, and save screenshots before the official rerun.
- The frozen 0.25 verdict is unchanged. The next acceptance run must use the corrected precondition, not this
  diagnostic, as its evidence.
