### 3.2 TTS 播完才结束（Task 17 R106）

- **开关与引擎**：`DebugSpeechToggle` 打开后日志 `P5_SPEECH_TOGGLE enabled=true speech=true`；冷启动后生产组合装配了 TTS 播放器（force-stop 旧进程时系统日志出现 `TextToSpeechManagerPerUserService … Unbinding TTS engine`）。
- **长回答**：用生产 `notify_user` 路径（`DebugToolCallInjector` 的 debug 传输 arm 固定合成文本，channel=both，`times=1`）产生一条 **324 codepoints** 的显示+语音回答；该文本在 400-codepoint 的眼镜 wire 上限内。固定合成文本不是模型生成，明确披露。
- **时序（同一回合 `fix-tts-1`，01:14:40–01:15:37）**：
  - `P3_HINT show … chars=324`（01:14:41.420）
  - `P5_SPEECH state=start hintId=… chars=324`（01:14:41.430）
  - `P3_HINT ack … status=Displayed`（01:14:41.469）
  - `P3_TURN end turn=fix-tts-1 outcome=COMPLETED code=- steps=1`（01:14:41.919）——回合结束在语音开始之后，符合预期
  - `P5_SPEECH state=cancelled hintId=… chars=324`（01:15:17.326）——**语音没有 `state=end`**；取消时刻恰好是该 324-char 提示的显示预算到期（`HintReadingBudget.readMillis` = 1.5 s + 21×1.4 s + 5 s = 35.9 s）
  - 01:15:37 CXR 链路丢失（`link lost: session…`），此后没有可判读的 cycle `continue/close` 或 `speech_timeout/no_display`。
- **机制**：`OutputArbiter.remove()` 在提示到期时**先停播再撤屏**（`speechHandle.cancel()`），因此只要 TTS 比显示预算长，音频就会被宿主取消；`ConversationCycle` 的 R106 等待只保证回合不提前续接/关闭，**不能**让被宿主取消的语音继续播完。`P5_SPEECH state=end` 未发生，所以“语音结束早于 cycle 继续/关闭”的排序无法在本轮成立；也没有观察到正常的 `speech_timeout/no_display`（链路先断）。
- **附加发现（记录，不修）**：同一验证中，模型自己产生的一条 **569-char** `notify_user`（channel=voice）因超过 400-codepoint 显示上限而未被显示/朗读（`P3_CONV no_display reason=not_displayed`），`P5_SPEECH` 未启动。长回答在产品的 400 上限处先被截断，是另一个产品边界。
- **判词**：**FAIL（长 TTS 仍未播完；宿主在显示预算到期时取消播放）**。短语音能否正常 `end` 未在“长回答”场景中成立；不把 `cancelled` 读成 `end`，也不把未测排序读成通过。
