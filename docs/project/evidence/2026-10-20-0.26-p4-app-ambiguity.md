## Root cause

`PackageManagerAppCatalog` enumerated `getInstalledApplications(0)`. On this K40 that returned **1** package
(`installedAll` via `MATCH_ALL` was also 1) even though `QUERY_ALL_PACKAGES` was granted. The same process's launcher
query returned **31** activities and `getLaunchIntentForPackage("com.android.settings")` was true, so the visibility
permission was not the problem: the enumeration API was.

The catalogue is now built from
`PackageManager.queryIntentActivities(Intent(ACTION_MAIN).addCategory(CATEGORY_LAUNCHER), 0)`, deduplicated by package,
with `resolveInfo.loadLabel` for the label. Device readback:

```text
P3_PACKAGEVIS installed=1 installedAll=1 launcher=31 settingsLaunchable=true fileLaunchable=true
P3_APPCATALOG total=30 fileish=2
  packages=com.android.fileexplorer=文件管理,com.google.android.documentsui=文件
```

The catalogue is now the same live launchable set as `open(list)` (30 vs 31 by query/parse details), instead of
"only EDITH".

## Ambiguity rule

The old resolver preferred a unique exact label over substring candidates. That silently opened
`com.google.android.documentsui` (label `文件`) while `com.android.fileexplorer` (`文件管理`) was also a plausible
target. P4 requires "≥2 candidates, not silent", so exact and substring matches are now one candidate set; more than one
match returns `APP_AMBIGUOUS` with all candidates. A new resolver test pins the two file apps; the old
"exact wins over substring" test is replaced by "exact does not hide a nearby candidate".

Device readback of the production `open("文件")`:

```text
P3_TOOLARG tool=open targetClass=label chars=2 relaunch=false
P3_OPENTARGET outcome=Refused code=APP_AMBIGUOUS candidates=2
```

No app was launched: the refusal is the intended result, not a silent pick.
