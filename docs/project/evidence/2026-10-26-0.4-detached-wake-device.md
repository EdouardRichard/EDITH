## 2. 修复轮 2 的生产修复（本轮唯一生产代码变化）

- **审查发现（语义，IMPORTANT）**：修复轮 1 把 `DetachGate.stopService` 接到
  `runCatching { SessionService.commandFromUi(context, SessionService.STOP) }`。`runCatching` 把任何异常吞掉，而 `commandFromUi` 自己又只发命令、不返回结果，因此 **`DetachGate.SESSION_STOP_FAILED` 在生产中不可达**：服务停止失败仍会保存模式并报 `stoppedSession=true`。
- **修复**：
  - `DetachGate.stopService` 由 `() -> Unit` 改为 **`() -> Boolean`**；运行态分支在 `stopSession()` 之后、`loadForWrite()`/`save()` 之前调用，只有返回 `true` 才算「服务确实被停止」；返回 `false` 或抛异常都按停止失败处理：**不写 blob、不移动 live gate、`stoppedSession=false`、返回 `SESSION_STOP_FAILED`**。该分支仍只覆盖 `Ready/Listening/Paused`；`Idle` 不停止任何东西（测试断言不再调用两个停止回调）。
  - `HostCompositionRoot.create` 改成**未包装的直连停止**：
    `stopService = { context.stopService(Intent(context, SessionService::class.java)) }`。
    `Context.stopService` 的契约是「停到一个正在运行的匹配服务才返回 true，否则 false」，所以 false 会真的变成失败可见；平台拒绝时它抛异常，也会被 gate 的 catch 转成 `SESSION_STOP_FAILED`。**不再重新派发 UI STOP 命令**，因此修复轮 1 记录里「同一条 UI 停止路径 / 最多 3 次 STOP 派发」的陈述作废。
  - **设备验证逼出的第二处修复**：只用 `context.stopService` 时，设备上出现了「服务已从 `dumpsys activity services` 消失、但 `edith.session` 通知记录仍在」的竞态——`SessionService` 的状态收集器在 gate 的停止之后又补发了一次「会话已开启」，而系统在 `onDestroy` 之前已把前台状态摘掉，单纯 `stopForeground(REMOVE)` 无法删掉这次补发。最终 `SessionService.onDestroy` 先取消收集器 scope，再 `stopForeground(REMOVE)` 并**直接 `NotificationManager.cancel(NOTIFICATION)`**。设备原始：竞态轮 `.local/task9/fix2race-d3-02-notification-later.txt`（记录仍在），最终轮 `fix2-d3-02-after-notification.txt` / `fix2-d3-04-after-notification.txt`（**0 条本包 NotificationRecord**）。
  - 目标行/服务/通知的最终效果由 §4.2/§4.3 的转储证明；正常「通知栏停止」路径仍走服务自身 `STOP` 分支，未改。
- **测试**：`DetachGateTest` **16 tests 全绿**——新增「服务停止返回 false 时拒保存」、保留「抛异常时拒保存」，顺序测试（stop → service stop → read → write）与 idle 不停止服务断言。`SessionService.onDestroy` 没有 JVM 覆盖，由设备证据承担。
- **全 app 模块单测**（最终代码）：`:phone-app:app:testDebugUnitTest` 与最终 build 同一次执行 → `BUILD SUCCESSFUL`；**142 XML / 1613 tests / 0 failures / 0 errors / 2 skipped**（`fix2-build-test.log`，22:46；XML 拷贝 `.local/task9/fix2-test-xml/`）。两项 skip 是不同原因、均为 `AssumptionViolatedException`：`EngineBundleProvisioningTest.aValidatedPathThatEscapesTheBundleRootIsRefused` 因 Windows 主机不能建符号链接；`EmbeddingTokenizerTest.every case in the publisher corpus encodes identically` 因 `.local/t6b2-corpus.tsv` 不存在。22:39 的 `fix2-full-app-test.log` 是最终编辑前的独立全量跑，早于 22:46 的 `SessionService.kt`/`HostCompositionRoot.kt` 最后一次编辑，不能当作最终代码的通过证据。
- 眼镜端/CXR、设置键、唤醒词、通知 channel 均未改。
