# 2026-10-15 B5 收口：真机上的"按语义排序"对照（头名随查询变，且可复现）

- **checkpoint**：`edith-0.2-phase-b-exec-20261015-11`
- **设备**：K40 `2696813b`（Android 13）；验收设备口径按 **D65**（K70 不单独验收）
- **要补的那一块**：B5 此前只能写"排序对照仍只有 JVM 证据"——真机上 `indexed=1`，**头名不可能变**，
  所以设备读数只到"相似度区间跟着相关性走"（[前一份证据](2026-10-14-b5-semantic-ranking-probe.md)）。
  本轮把**同进程索引里的记忆凑到 2 条**，于是"头名是否随查询变"成为可观测的量。

## 1. 协议

同一个 App 进程（索引只装本进程写过的条目），四个回合、每条一次注入（`edith.DEBUG_INJECT`，**注入语音不是佩戴者发声**）：

| 回合 | 注入件（自造语料，P3.4） | 作用 |
|---|---|---|
| 1 | `E01-keep-tea.wav`（"我喜欢喝茶"类偏好句） | 写入并**索引**第 1 条 |
| 2 | `E04-keep-wake-time.wav`（"我通常早上七点起床"类事实句） | 写入并**索引**第 2 条 |
| 3 | `R1b-query-tea.wav`（"我想喝点什么"） | **查询 A**（与第 1 条相关） |
| 4 | `query-wake-time.wav`（"我几点起床"，本轮 SAPI 合成） | **查询 B**（与第 2 条相关） |
| 5 | `R1b-query-tea.wav`（重复查询 A） | 对照：头名是否回到 A 的那条 |

## 2. 读数（原文照抄，只删 id 中段；`P3_MEMORY inject=` 只记计数/区间/id，不含正文）

```
16:07:46  inject=n=5 chars=132 via=lexical  bucket=none   indexed=0 ids=memory:cad78234-…,43f34796-…,4abfef8b-…,48209212-…,17387c39-…
16:07:49  P3_MEMORY write=n=1 kind=PREFERENCE source=AUTO      ← 第 1 条写入并索引
16:07:58  inject=n=5 chars=132 via=semantic bucket=0.4-0.5 indexed=1 ids=memory:cad78234-…,43f34796-…,4abfef8b-…,48209212-…,17387c39-…
16:08:05  P3_MEMORY write=n=1 kind=PREFERENCE source=AUTO      ← 第 2 条写入并索引
16:08:14  inject=n=5 chars=144 via=semantic bucket=0.5-0.6 indexed=2 ids=memory:cad78234-…,…   ← 查询 A：头名 = cad78234
16:08:29  inject=n=5 chars=144 via=semantic bucket=0.8-0.9 indexed=2 ids=memory:43f34796-…,…   ← 查询 B：头名 = 43f34796
16:08:42  inject=n=5 chars=144 via=semantic bucket=0.5-0.6 indexed=2 ids=memory:cad78234-…,…   ← 查询 A 复现：头名回到 cad78234
```

**读出来的三件事**：

1. **头名是查询的函数**：同一个库、同一个索引（`indexed=2` 全程不变），
   查询 A 的头名是 `cad78234-…`，换查询 B 变成 `43f34796-…`，**再问一次 A 又回到 `cad78234-…`**。
   ⇒ 设备上的生产检索**按查询的意思排序**，而不是按一个与查询无关的固定分数。
2. **区间与排序一致**：查询 B 命中更强（`0.8-0.9`，因为它几乎逐字问回那条事实），查询 A 更间接（`0.5-0.6`）。
3. **冷索引仍然如实标 `lexical`**：第 1 回合 `indexed=0 via=lexical`——重启后的第一个回合不冒充语义排序
   （这正是上一轮被真机读数修掉的那个探针缺陷）。

**一个实现细节值得记下**：第 1、2 回合的 `write` 落库时，两条的 id 都**已经**在库列表里出现过 ⇒
`MemoryLog.record` 的去重把这两句并到了既有条目上，而 `MemoryModule.remember` 仍然 `retriever.index(entry)`，
所以**既有条目被重新索引**、成为可语义检索的那两条。这不是缺陷，是去重与索引的既定组合；写在这里免得下次误读。

## 3. 边界（不得读成已完成）

- 语料是**自造**的（P3.4 的 E01/E04，非佩戴者数据）；本文件**不记录任何正文**，只有 id、计数与相似度区间。
- **id ↔ 记忆的对应是靠"翻转本身"推出来的**（回合 1 写的是茶、回合 2 写的是起床时间，头名随对应查询翻转且可复现），
  不是靠读库正文——读库会把正文带进证据，违反"只记计数与 id"。
- 库是**混合**的：`n=5` 里只有 2 条在索引里，其余 3 条按字面排在语义头之后；本行测的是**头名**，不是全序。
- 未测：真实佩戴者语料下的排序质量；索引 ≥3 条时的全序；embedding 单次前向延迟仍是既有未达标项（~584 ms 量级）。
- 单机（K40）；按 **D65** 不要求 K70 复验。
