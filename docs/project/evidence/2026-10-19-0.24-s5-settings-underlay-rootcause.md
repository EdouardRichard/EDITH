## 0. 结论摘要（先读）

1. **面板不是“没打开”**：`PANEL_OPEN accepted`、`WAKE_LOCK acquire`、`OVERLAY added`、`OVERLAY laid_out`、`PANEL_SHOWN sent=true` 全部正常；随后平台把该窗口 `mForceHideNonSystemOverlayWindow` 置真并强制隐藏（`isOnScreen=false`，`Surface: shown=false`）。
2. **与 EDITH 无关的第三方悬浮窗同样被隐藏**：S1 遗留的独立探针 `com.sheen.rokid.glasses.overlayspike`（普通应用、无 EDITH 代码、同一个 `TYPE_APPLICATION_OVERLAY` 形状）在 Settings 上得到完全相同的 `mForceHideNonSystemOverlayWindow=true` / `isOnScreen=false`，前后截图与 Settings-only **哈希相同**。因此隐藏原因不是我们的 scene、焦点或窗口生命周期。
3. **ANR 是平台的输入/焦点级联**：面板强制隐藏后，`mCurrentFocus=null`、`InputDispatcher FocusedWindows: <none>`；此时注入 BACK 得到 `Dropping KEY event because there is no focused window` → `ANR in ActivityRecord{…GlassesActivity…} Reason: Application does not have a focused window`。面板窗口早在注入前 30 s 就是 `isOnScreen=false`，所以面板不可见不是 BACK 造成的；BACK 只是触发输入看门狗。
4. **无产品修复、无提交**；平台没有给普通应用留下合法绕过路径（§4）。controller 已把 U-19 改为 `Partial` 并把 Settings 分支单列为 `Failed (platform limitation)` 残留（§8）。

## 4. 平台机制：为什么没有产品可修项

### 4.1 权限与窗口标志（设备读回）

```text
dumpsys package com.android.settings:
  android.permission.HIDE_NON_SYSTEM_OVERLAY_WINDOWS: granted=true
  android.permission.SYSTEM_ALERT_WINDOW: granted=true
dumpsys package com.sheen.rokid.glasses:
  仅请求 SYSTEM_ALERT_WINDOW（app-op allow 由 adb 设置）；没有 HIDE_* 权限
dumpsys window（我们的 session）:
  Session Session{ea51b50 26787:u0a10080}: mNumWindow=1 mCanAddInternalSystemWindow=false …
```

### 4.2 AOSP Android 12（`android-12.0.0_r1`）源码链

- `Window.setHideOverlayWindows(boolean)`（API 31）要求 `HIDE_NON_SYSTEM_OVERLAY_WINDOWS` 或 `HIDE_OVERLAY_WINDOWS`，并设置 `SYSTEM_FLAG_HIDE_NON_SYSTEM_OVERLAY_WINDOWS`（`core/java/android/view/Window.java:1004-1014`）。
- `WindowState.hideNonSystemOverlayWindowsWhenVisible()` 只有在窗口带该 private flag **且** `mSession.mCanHideNonSystemOverlayWindows`（`Session.java:127-128`，由上述权限决定）时才为真。
- `WindowManagerService.updateNonSystemOverlayWindowsVisibilityIfNeeded()` 把“正在显示且带 flag”的窗口加入 `mHidingNonSystemOverlayWindows`，并对所有窗口调用 `setForceHideNonSystemOverlayWindowIfNeeded(true)`；`dumpsys window` 的 `Hiding System Alert Windows:` 就是这个列表。
- `WindowState.setForceHideNonSystemOverlayWindowIfNeeded(true)` 对 `SYSTEM_ALERT_WINDOW`/`TYPE_TOAST` 类窗口调用 `hide()`；只有 `mSession.mCanAddInternalSystemWindow`（`INTERNAL_SYSTEM_WINDOW`，signature）或满足 `isSystemApplicationOverlay()`+`mCanCreateSystemApplicationOverlay` 的系统 application overlay 才豁免。**我们的 session `mCanAddInternalSystemWindow=false`，产品也没有 `HIDE_*` 权限。**
- `hide()` 清掉 policy visibility → `isVisibleByPolicy()=false` → `isOnScreen()=false`；`show()` 在 `mForceHideNonSystemOverlayWindow` 为真时直接拒绝恢复。
- 第三方无法改成别的窗口类型：`TYPE_APPLICATION_OVERLAY` 之外的系统窗口类型需要 `INTERNAL_SYSTEM_WINDOW`。因此**没有合法的产品 workaround**；不要用系统安全旁路去“修”它。

逐行原文见 [`raw-window-manager-evidence.txt`](assets/2026-10-19-0.24-s5-settings-underlay/raw-window-manager-evidence.txt)（AOSP 段）。

### 4.3 范围（已测与未测）

- **已测**：`com.android.settings` 会设置该 flag 并被平台隐藏覆盖其上的第三方 overlay。
- **权限面**：目标包 `dumpsys` 读回显示 `com.android.permissioncontroller`、`com.android.packageinstaller`、`com.android.managedprovisioning`、`com.android.certinstaller`、`com.android.vpndialogs`、`com.android.companiondevicemanager` 也持有 `HIDE_NON_SYSTEM_OVERLAY_WINDOWS: granted=true`；**是否在这些应用的窗口上设置 flag 未测**。`com.rokid.os.sprite.launcher` 同样持有权限，但其窗口 dump 没有 `pfl=HIDE_NON_SYSTEM_OVERLAY_WINDOWS`，所以面板在 launcher 上正常；`com.android.soundrecorder` 两个都没有，所以 SoundRecorder 分支通过。
- 不要外推成“所有系统应用都会隐藏面板”；触发条件是**持有权限 + 窗口显式设置 flag**。

### 5.3 为什么焦点是 null（平台焦点策略）

`DisplayContent.mFindFocusedWindow` 从顶层向下找 `canReceiveKeys()` 的窗口；一旦遇到“root task 在聚焦 app 的 root task 之下”的活动窗口就立即 `mTmpWindow = null` 并停止（源码注释：“App root task below focused app root task. **No focus for you!!!**”）。本状态下：

1. 聚焦 app = 透明 scene（`GlassesActivity`，CXR 会话要求其保持 resumed，业主选项 A）；
2. 它的窗口 `NOT_FOCUSABLE`，不能取焦；
3. force-hidden 的 `EDITH-PANEL` 不能取焦；
4. 唯一可聚焦的 Settings 窗口在 scene 的 task 之下 → 平台直接停止搜索，返回 null。

这是平台的焦点策略，不是我们的键盘/窗口代码 bug；把 scene 窗口改成可聚焦会更糟（按键与 BACK 会被 scene 吃掉，BACK 会 finish scene，直接 `GLASSES_APP_EXIT`），也不是 CXR 允许的做法。

### 5.4 关于“注入”是不是测试装具的问题

- 用的是与 Task 21 §7.2 **完全相同**的 `adb shell input keyevent KEYCODE_BACK`；没有改探针、没有用 `input tap/text`。
- ANR 的判定是平台在“聚焦应用没有聚焦窗口”时对 pending key 的看门狗；注入只是触发这个已存在的状态（面板 30 s 前就已经 `isOnScreen=false` 且 `FocusedWindows: <none>`）。
- 因此 **C 不是我们的测试装具缺陷**；没有改探针或产品。物理侧键在同一状态下是否同样触发 ANR：`NotMeasured`（没有物理压力/按键测量），但输入层的“无聚焦窗口”条件本身与注入方式无关。

## 7. 影响与残留

- **产品状态错位（真实影响）**：面板实际不可见，但眼镜侧已经发出 `PANEL_SHOWN`、持有 600 s 屏幕唤醒锁、控制器保持“可见”；手机侧开始 listening（`P3_CONV listen`）。wake + 静默（U-14 官方行为：空白 ASR 取消 10 s 计时器）时，不可见面板可能一直持有唤醒锁/会话直到关闭或 600 s 锁超时。
- **按键即可能杀会话**：该状态下没有聚焦窗口；实测 BACK → `Dropping KEY event` → ANR → 进程死 → `GLASSES_APP_EXIT`/`P3_CXR disconnect link=lost`。U-19 的 “overlay over any app” 不成立。
- **范围残留**：只实测了 Settings。其他持有 `HIDE_NON_SYSTEM_OVERLAY_WINDOWS` 的平台应用（PermissionController/PackageInstaller/ManagedProvisioning/CertInstaller/VpnDialogs/CompanionDeviceManager）是否同样设置 flag 未测；launcher 持有权限但不设 flag（正常），SoundRecorder 两者都没有（正常）。不要外推成“所有系统应用”。
- **系统层不可绕过**：见 §4；普通应用不能拿 `INTERNAL_SYSTEM_WINDOW`/`HIDE_*`，也不能换系统窗口类型。
