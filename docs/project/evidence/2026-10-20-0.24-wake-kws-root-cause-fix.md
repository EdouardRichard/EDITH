## 0. TL;DR

1. **根因不是模型损坏、不是 VAD 截断、不是自音频抑制、也不是关键词拼写**。三项正负对照都通过：
   - 原语路径正对照：模型自带 `en_0.wav` + `LIGHT_UP/LOVELY_CHILD` 关键词，在同一构建、同一 APK 资产上 **命中 `LIGHT_UP`**；
   - 配置关键词（`伊迪丝`/`EDITH`）对同一份唤醒录音，在**流从文件开头开始**时**命中了**（en 5/5，zh 1/1）；
   - 注入 5 次 0 命中时，ASR/VAD/自音频门都正常工作（`P3_ACOUSTIC`、`P3_ASR`、`P3_FRAME`）。
2. **根因（行为层面已测）：KWS 流对唤醒词相对 160 ms 分块边界的“相位”敏感。** 同一份录音、同一套资产、同一个原生 spotter：
   - 单流在 0 ms 前缀时命中，但加 5 s 安静前缀后 **5/5 全不命中**；
   - 20 ms 步进的偏移扫描是**结构性**的：0 ms 中，20/40/60/80/100 ms 全不中，120–180 ms 又中；
   - 单流在其跑过的 **9 个英文**对齐/前缀用例里 **8 个不中**（仅 0 ms 命中）；中文只补测了单流 0 ms（命中）。
3. **修复：同一原生 spotter 上并行 8 条错相流（每 20 ms 一条），覆盖全部 8 个相位；引擎 reset 后重新错开。**
   - 设备探针：8 流 **12/12** 用例命中（每条 3–4 次独立命中）；4 流 11/11，但生产里仍漏过 1/12；
   - 生产注入：8 流构建 **7/7 次唤醒**（6 次连续 + 1 次 60 s 空闲后），`P3_WAKE word=EDITH` → `PANEL_SHOWN accepted`。
4. **旧分析里的 2× 现场流在新构建上没有复现**：冷启动与二次 `开始` 后都实测 **≈50.0–50.4 callbacks/s × 640 B = 32 KB/s（1×）**，`dupConsecutive=0`。已在传输层加 `P3_CXR_AUDIO` 计数，下次现场若再出现 2× 可直接判别“重复投递 / 两路流”。
5. **全量 JVM**：**340 suites / 3 276 tests / 0 failures / 0 errors / 1 skipped**（`--rerun-tasks`，JUnit XML 聚合，排除 `probes/`、`third_party/`；手机 app 模块单列 **104 suites / 1 041 tests / 0 failures / 1 skipped**）。
6. **未测边界**：真人现场麦克风唤醒；8 流的长期 CPU/内存与功耗；2× 的现场复现；`wake-zh.wav` 命中的标签是 `EDITH`（英文 AH0 行），不是 `伊迪丝` 行（功能上仍唤醒，日志标签如此）。

## 3. 关键测量：相位敏感

### 3.1 探针（`DebugKwsProbe`）

debug-only 广播，直接构造**真实** `KeywordSpotter`（打包资产 + 生产同款 `SherpaKeywordSpotterFactory`），把 WAV 按 20 ms 块喂入，日志只记标签与计数：

```powershell
adb -s 2696813b shell "am broadcast -a edith.DEBUG_KWS \
  -n com.sheen.rokid.phone/.debug.DebugKwsProbe \
  --es path /data/local/tmp/edith-audio/wake-en.wav \
  --el silenceMillis 5000 --ei silenceLevel 30 \
  --ei streams 8 --ei streamStride 1"
```

- `silenceMillis`：在录音前先喂 N ms 的“安静前缀”；`silenceLevel`：前缀幅度（LSB，0=数字零，30≈−60 dBFS）；
- `streams`/`streamStride`：并行流数与错开帧数（`streams=1` 即旧行为）。

### 3.2 正对照

```text
P3_KWS hit=LIGHT_UP tokens=5
P3_KWS_PROBE file=en_0.wav chunks=331 decodes=40 labels=2 hits=1 observed=LIGHT_UP
```

### 3.3 单流：前缀/偏移矩阵

**en，新进程逐次，`silenceLevel=30`，`streams=1`**：

| 前缀 | 结果 |
|---:|---|
| 0 ms | **命中** |
| 20 / 40 / 60 / 80 / 100 ms | 0 |
| 120 / 140 / 160 / 180 ms | **命中** |
| 500 ms | **命中** |
| 1 000 ms | 0 |
| 2 000 / 3 000 / 4 000 ms | **命中** |
| 5 000 ms | **0（同进程重复 5 次，5/5 不中）** |
| 6 000 ms | 0 |
| 8 000 / 10 000 ms | **命中** |

**判读**：不是“前缀越长越差”的单调关系，而是**唤醒词落在模型分块/解码状态的哪个相位**决定命中。单流在其跑过的 9 个英文用例里 8 个不中；这解释了历史注入命中率（2/3、8/18、0/5）的波动。

### 3.4 多流：相位覆盖

| 配置 | en 用例（0/20/40/60/80/100/1000/5000/6000 ms） | zh 用例（0/1000/5000 ms） | 合计 |
|---|---|---|---|
| 1 流 | 仅 0 ms 命中（20–100、1000、5000、6000 均 0） | 0/1（仅测 0 ms 时命中） | 差 |
| 4 流 / stride 2 | **9/9 命中** | **2/2 命中** | **11/11** |
| 8 流 / stride 1 | **9/9 命中**（每条 3–4 次） | **3/3 命中** | **12/12** |

探针单次耗时（含 8.9–14.9 s 音频，K40，冷进程、含 JIT）：4 流 3.58–6.66 s；8 流 4.78–9.66 s。**这是 KWS 解码路径的探针耗时，不是生产 CPU/功耗测量**（见 §8）。

## 4. 修复

### 4.1 引擎：同一 spotter，多条错相流

`phone-app/perception/audio-runtime/src/main/kotlin/com/sheen/rokid/audio/WakeWords.kt`：

- `KeywordSpotterWakeWordEngine` 增加 `streams` / `streamStrideFrames`；
- 第 `j` 条流在全局第 `j × stride` 帧创建，之后接收同一批帧 → 各流的分块边界相对唤醒词错开；
- 命中后**就地** `reset(stream)`（不释放）；同帧多流报同一词时 `LinkedHashSet` 去重；
- `reset()` 释放全部流并把帧计数归零，下一次 `accept` 重新从 0/1/…/7 帧错开（**不重新错开就会在静音释放后坍缩成同一相位**）；
- 生产常量：`PHASE_DIVERSITY_STREAMS = 8`、`PHASE_DIVERSITY_STRIDE_FRAMES = 1`（8 条流覆盖 8 个 20 ms 相位）；单测默认 `1/1` 保持旧形状。

### 4.2 生产接线

`phone-app/app/src/main/kotlin/com/sheen/rokid/phone/app/HostCompositionRoot.kt` 的 `AudioChainEngines.wakeDetector`：

```kotlin
KeywordSpotterWakeWordEngine(port, keywordAssets.keywordsArgument,
    streams = KeywordSpotterWakeWordEngine.PHASE_DIVERSITY_STREAMS,
    streamStrideFrames = KeywordSpotterWakeWordEngine.PHASE_DIVERSITY_STRIDE_FRAMES)
```

模型仍只加载一次（一个 `KeywordSpotter`），复制的是每条流的 decoder 状态；VAD/ASR/门控路径未改。

### 4.3 观测（保留）

- `CxrAudioAdapter.onAudioReceived`：`P3_CXR_AUDIO callbacks=… bytes=… dupConsecutive=… lastLength=…`，每 250 次一条（≈5 s）；只计数，不记音频。
- `OwnedKeywordSpotterPort`：`P3_KWS frames/ready/decoded/hits` 每 2 000 次 `isReady` 一条；命中记 `P3_KWS hit=<label> tokens=<n>`。
- 新增 debug-only：`DebugKwsProbe`（`edith.DEBUG_KWS`）、`DebugSessionControl`（`edith.DEBUG_SESSION`），均在 `src/debug/AndroidManifest.xml`，release 不含。

### 4.4 测试

- `WakeWordDetectorTest` 新增 3 条：
  - `keyword engine keeps a hit that only a later stream phase produces`（单流会漏、错相流能留住）；
  - `keyword engine staggers streams by the configured stride and re-staggers after reset`（第 j 条流接收 8/6/4/2 帧；reset 后重新 8/6/4/2）；
  - `keyword engine deduplicates the same word reported by several streams in one frame`。
- `FakeKeywordSpotterPort` 增加 `hittingCreations`，模拟“只有某个相位能命中”。
- `KeywordSpotterDeviceTest` 的过期断言由 `IY1 D IH0 TH` 更正为资产实际值 `IY1 D AH0 TH`（该 androidTest 当前**无法构建**，见 §8）。

## 6. 2× 现场流：本次未复现，诊断已留下

### 6.1 冷启动

```text
P3_CXR_AUDIO callbacks=250 bytes=160000 dupConsecutive=0 lastLength=640
（250 次 / 5.00 s = 50.0 次/s × 640 B = 32 KB/s = 1×）
```

### 6.2 二次开始（`DebugSessionControl stop/start`，`generation=2`）

```text
16:50:25.953  P3_AUDIO state=armed generation=2
16:50:30.367  P3_CXR_AUDIO callbacks=1250 bytes=800000 dupConsecutive=0 lastLength=640
16:50:35.324  P3_CXR_AUDIO callbacks=1500 bytes=960000 dupConsecutive=0 lastLength=640
（250 次 / 4.96 s = 50.4 次/s；1×）
```

**结论**：0.24 分析里的 ≈100 次/s（64 KB/s）**没有**由“同进程二次开始 / 回调重复安装”产生；本次冷启动和二次开始都是 1×、零重复块。`P3_CXR_AUDIO` 已保留，下次现场若再出现 2×，`dupConsecutive` 直接区分“同一块重复投递”与“两路流交织”。

### 6.3 未复现的边界

- 0.24 现场的眼镜系统侧在 22:35 曾打开官方 `ai_assist` 场景并 force-stop `edith.glasses`；本轮没有复现该场景（无厂商功能键注入路径，未用 `input keyevent` 硬凑）。
- 因此 **2× 的现场成因仍未定**；本修复不能补偿 2×（时间压缩后的音频对所有相位流都失效）。这是重新验收前需要知道的残余风险。

### 6.4 一次 UI 探针尝试（如实记）

用 `a11yprobe` 点「菜单」成功；点「停止/开始」返回 `click_refused`（节点匹配、点击被拒），未用 `input tap` 替代。会后改由 `DebugSessionControl` 调生产 `start/stop` 完成二次开始。期间 MIUI 的 force-stop 清空了 `enabled_accessibility_services`，已按“读现值 → 同时恢复探针与生产服务 → `dumpsys accessibility` 验证绑定”恢复（生产服务 Bound；探针服务 Enabled，活动启动后绑定）。

## 8. 明确未测 / 边界

1. **真人现场麦克风唤醒未测**：本记录只把录音注入到**同一条已证明可用的 PCM 管线**；声学耦合、发音、佩戴位置仍属未测（`NotMeasured`）。
2. **8 流的长期 CPU / 内存 / 功耗未测**：探针耗时不能替代生产测量；8 条 decoder 状态的内存增量未读。
3. **2× 现场流未复现**：新构建冷启动/二次开始均 1×；官方 `ai_assist` 场景未构造；2× 若复发，本修复不解决。
4. **`wake-zh.wav` 的命中标签是 `EDITH`**：中文录音在本次模型上由英文 `IY1 D AH0 TH` 行检出（`tokens=4`），不是 `伊迪丝` 行。功能上仍能唤醒并弹面板；日志标签如实保留。中文行的单独召回仍差（历史 2/3），本次未再调关键词。
5. **androidTest 构建被锁文件阻塞**：`:phone-app:app:assembleDebugAndroidTest` 因锁定依赖 `com.google.ai.edge.litert:litert-npu-runtime-mediatek:2.3.0` 无法解析而失败（2026-10-20），故 `KeywordSpotterDeviceTest` 未跑；其过期断言已在源码更正，但**未在设备上执行**。
6. **未重跑 0.24/0.25 验收语料**；不把本记录的注入 PASS 读成 U-13/U-15 或 0.25 语料 PASS。
7. 未提交、未 push、未打 tag；工作树里 0.26 锁屏等未提交改动保持原样。
