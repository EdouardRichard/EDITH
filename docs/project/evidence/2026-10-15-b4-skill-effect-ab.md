- **checkpoint**：`edith-0.2-phase-b-exec-20261015-11`
- **设备**：K40 `2696813b`（Android 13；验收设备口径按 **D65**）
- **业主判据（2026-10-15 原话）**：**"从完成任务耗时、任务完成效果两个方向评估。有 SKILL 耗时低，则认为有效果。

  因此 **B4 不升级**，本文件把读数与混淆项全部记下来。

## 1. 装置

- **臂＝文件在不在**：App 每个回合读 `/sdcard/EDITH/skills/`，所以把 `device-task-discipline.md` 在
  `skills/`（ON）与 `skills-off/`（OFF）之间 `mv` 就是切换臂；**每个回合都有一条自证行**：
  `P3_SKILL load files=1 skills=1 enabled=1`（ON）或 `files=0 skills=0 enabled=0`（OFF）——上表每一行的臂都由它确认。
- **任务**（Windows SAPI 合成、注入、**非佩戴者发声**；每条含唤醒词 ⇒ 一次注入一个唤醒回合）：
  - `t1`："打开设置。"
  - `t2`："帮我设一个明天早上七点的闹钟。"
  - `t3`（两步）："先打开设置，再帮我设一个明天早上七点的闹钟。"
- **判据（全部来自生产日志、不含正文）**：
  - 完成效果＝该回合出现**预期工具调用且 `ok=true`**（`P3_TOOL call=<name> ok=true`）＋`outcome=COMPLETED`；
  - 耗时＝`P3_TURN start` → `P3_TURN end` 的墙钟；
  - 附带：`P3_NOTIFY`（SKILL 的通知纪律可观测），以及 `steps=`。
- **为什么选这两个动作**：`open_settings`=L0、`set_alarm`=L1，两者都**不在确认门之后**（无需点屏），
  且日志只记动作名与结果、不记参数 ⇒ 判据可观测且不引入正文。

## 3. 按业主的两个方向判读

**① 完成效果：没有显示出效果。**
合并 `t3` 全部有效样本：**有 SKILL 3/5，无 SKILL 2/6**（33%）。方向上偏"有 SKILL 更容易动手"，但
（a）远达不到判据说的"有 SKILL 能完成、无 SKILL 没完成"；（b）**重启后无 SKILL 那一臂 2/2 全中**，
说明**决定性因素是回合/进程状态**（重启后头几个回合更容易动手），而不是臂。
另外：**两步任务的第二步（`set_alarm`）在任何一臂都没有被执行**（`steps` 从未到 2）——
SKILL 的"一件一件做、每件确认"这条在设备上没有可观测的效果。

**② 耗时：没有显示出"有 SKILL 更低"。**
动手的回合**更慢**（多一次模型往返：ON 15.4 / 17.3 s），不动手的回合更快（8.8–10.6 s）；
只看"完成了的回合"：ON 4.9–17.3 s（跨度大）、OFF 6.2–8.7 s。**没有任何一致的优势方向。**
⇒ 业主判据里的"耗时低"在本装置上不成立；而且这条判据本身有个结构性陷阱：**什么都不做的回合天然更快**，
所以耗时只有在"两边都完成"时才可比，而这里两边都完成的样本只有重启后的 2 对。

**③ 附带读数（SKILL 的通知纪律）**：两条纪律（完成用 `both`、中间步骤不出声）在本轮**都不可测**——
配置的模型在**任何一臂**都没有调用 `notify_user`（每回合都是 `P3_NOTIFY fallback=screen`，即 §6.2 兜底）。
这与 08/06 会话的既有读数一致（"模型从不选 notify_user"）。

## 4. 一个必须一起记的结构性事实：默认白名单是空的

`SmartSettings` 的默认值是 `maxLevel="L1"` + **`whitelist=emptyList()`**。实测表明
**L0/L1 的动作仍然在模型工具表里**（`open_settings` 真的被调用了），所以"动作不可达"不是本次的阻塞；
但如果某人把策略收紧到只认白名单，SKILL 里那些"先问再做/一次一件"的条款就会**整段不可达**。
这条不影响本轮判读，记下来免得下次误判。

## 5. 一起记下的一个缺陷观察（本轮由脚本造成，不修）

`t3 rep4`（ON）那一轮 **90 s 内没有结束**；脚本随即注入了下一轮 ⇒ **两个回合重叠**。此后
**连续两轮**以 `outcome=FAILED code=PLUGIN_RUN_THREW` 快速失败，取到的那一行是：

```
P3_RUN error=ConfigurationRejected code=Explicit context exceeds safe budget or is malformed
P3_CONTEXT route=WAKE instructions=250 history=14 historyChars=1626 memory=5 tokens=1930 budget=2808 over=false
```

**注意 `over=false`、`tokens < budget`**：被拒的不是"超预算"，而是**转写形状**——
两个回合交错各自写下 user 半边，于是出现**相邻两条 user**，`ContextBudgeter` 的交替规则直接拒绝
（与 08 交接里"真因未截获的瞬态"同一族；那一次的原因是"失败回合只落了 user 半边"，已在 `8159c00` 修掉，
但**"两回合交错"这条路径没修**）。判定：**本轮不是产品回归**（是我的脚本在上一轮未结束时又注入造成的），
但它是**可被真实用户触发**的（第一次回合还在跑时又说一次唤醒词），故**记录不改**，留给后续裁决。

## 6. 结论与建议

- **B4 不升级**：按业主的两个方向都没有显示出 SKILL 的效果；本行保持 `ImplementedUnverified`，
  并把"效果未显示"和上面的读数一起记在行内（而不是含糊地写"未测"）。
- **若要真做出效果**，需要换判据而不是加样本：挑一条**确定性可观测**的 SKILL 条款（例如"`set_alarm` 参数
  必须 24 小时制整数"或"同一工具连续失败两次就停手"）做**多次重复**（≥20 次/臂）的单变量对照，
  或者换一个**更听话/更爱调工具**的档案；本轮这种"整份 SKILL 一起上、任务自由发挥"的设计，
  信噪比被模型自身的波动吃掉了。
- 未测（本行为此仍不算闭环）：`t2` 的第二步执行、通知纪律条款、以及第 5 节那条交错路径的修复后复验。
