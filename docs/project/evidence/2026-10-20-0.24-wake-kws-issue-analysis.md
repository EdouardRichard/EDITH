## 0. TL;DR（当前结论）

1. **音频确实到达手机端**：现场 PCM 连续进入 `P3_FRAME` 计数（`overflow=0`、`unknownFormat=0`），VAD/ASR 正常消费；注入路径的逐块对账也完全吻合。
2. **到达的现场音频形态异常**：帧率 ≈ **100 帧/秒 × 640 B/帧 = 64 KB/s**，约是验证格式（16 kHz mono = 32 KB/s、50 帧/秒）的 **2×**；注入路径为 **1×**（≈52 帧/秒）。成因待查（重复投递 / 双流 / 速率差异尚未区分）。
3. **更关键**：当前安装构建/进程里，**KWS 对 5 次已知唤醒录音的干净注入 0 命中**（`P3_WAKE=0`、`P5_CHIME=0`），而同一份录音在 2026-10-18 构建上注入命中过（`P3_WAKE word=EDITH`）。因此 F-01 **不能只归因于"现场声学/发音"**，检测路径本身当前不产出命中。
4. **KWS 模型文件未损坏**：设备安装 APK 内 6 个 `assets/kws/*` 文件与干净构建逐文件 SHA-256 一致。
5. **VAD 不截断 KWS 输入**（代码级）：KWS 引擎每帧都收到音频，VAD 只负责"连续静音 1.5 s 后重置 KWS 流"。
6. **未定**：0 命中是"长进程/会话生命周期状态"还是"当前构建回归"；2× 流成因；需应用重启 A/B 与诊断计数（见 §8）。
7. 截至本记录，**0.24 的 wake PASS 证据全部来自注入路径**（S1 门禁、S5 走查），**真人现场麦克风唤醒没有正命中证据**。

## 3. 假设核查

### 3.1 "KWS 模型/资源出问题" —— **排除**

见 §1.3：安装包与干净构建的 6 个 KWS 资源逐文件 SHA-256 相同；应用启动时（15:58:32.826）记录到 `KeywordSpotter_newFromAsset` 且其 config 指向 `kws/...` 资产路径。模型文件未损坏、未缺失。

### 3.2 "VAD 截断了 KWS" —— **排除（代码级）**

- KWS 生产喂帧路径：`phone-app/app/src/main/kotlin/com/sheen/rokid/phone/audio/AudioIngressLoop.kt` 的 `tick()`：
  `frames.forEach { frame -> wake?.accept(frame); pipeline.accept(frame) }`（约 L244–L247）——同一条音频流先喂 wake、再喂语音管线。
- `WakeWordDetector.accept`（`phone-app/perception/audio-runtime/src/main/kotlin/com/sheen/rokid/audio/WakeWords.kt` 约 L226–L245）中 **每一帧都调用 `engine.accept(frame)`**；VAD 只用于"speech 之后连续静音 ≥1.5 s 时重置 KWS 流"，不参与喂帧（该文件 L189–L211 的 KDoc 也明确说明了 D11 的这一设计）。
- 因此 VAD 无论怎么判，都不会减少 KWS 收到的帧。

### 3.3 "音频没到手机" —— **排除**

见 §2.1 的 `P3_FRAME` 计数（连续、零溢出）、`P3_ACOUSTIC`（有真实语音段）、`P3_ASR`（能出字）；注入路径的逐块对账（§4）也精确吻合。

### 3.4 "现场音频形态异常（2×）" —— **成立，成因未定**

现场流实测约 **2× 实时字节率**（见 §5.2），注入流为 1×。是否/如何导致 KWS 不命中尚未分离；由于注入（1×）同样 0 命中，2× 不是当前唯一解释。

## 4. 注入对照实验（关键证据）

### 4.1 仪器

- debug-only 广播：`am broadcast -a edith.DEBUG_INJECT -n com.sheen.rokid.phone/.debug.DebugAudioInjector --es path /data/local/tmp/edith-audio/<file>.wav`。
- 仪器行为（`phone-app/app/src/debug/.../DebugAudioInjector.kt`）：停止眼镜麦克风流（`P3_INJECT state=ambient_stopped`）→ 向**同一条** `PcmIngress` 按 20 ms 一块、640 B/块（16 kHz mono 20 ms）注入 → 恢复（`ambient_restored`）；只记录计数与文件名，不记录 PCM。
- 因此注入路径 = **干净 1× 已知音频**，可把"现场声学/麦克风/传输交织"从问题里拿掉。

### 4.2 结果（2026-10-19 23:10–23:13，会话 generation=4）

| 注入 | 块数 | 仪器读数 | `P3_WAKE` |
|---|---:|---|---|
| `wake-zh.wav`（23:10:13） | 476 | `accepted=476 drained=true` | **0** |
| `wake-en.wav`（23:10:51） | 444 | `accepted=444 drained=true` | **0** |
| 再次注入 3 次（en/zh/en，约 23:13） | 444+476+444 | 投递由帧计数精确核对（见下） | **0** |
| 合计 5 次 | 2 284 | 全部被消费 | **`P3_WAKE`=0、`P5_CHIME`=0** |

**投递精确核对**：23:14:01.407 `P3_FRAME frames=194991`、`accepted=192707`，差值 **2 284** = 476+444+444+476+444（五次注入块数之和，逐块对应）。注入块由仪器直接写入 ingress、不计入 `accepted`（`accepted` 只统计 CXR transport 侧 offer），故该差值正好是注入块数 ⇒ **5 次注入的音频一个不少地进入了同一条管线**。

**注入期间帧率**：23:10:13.069 `frames=174545` → 23:10:17.826 `frames=174795`，Δ250 帧 / 4.757 s ≈ **52.6 帧/秒**（1×，符合 20 ms/帧；ambient 已停）⇒ 应用内轮询/分帧正常。

**注入音频确实被处理**：注入窗口内有 `P3_ACOUSTIC label=Speech` 与 `P3_ASR revision=0/1 ... chars=1/4 ...`（例：23:10:15.046 Speech；23:10:15.371/15.950 ASR；23:10:21.053/21.287 ASR）。

## 5. 音频到达证据与 2× 异常

### 5.1 到达证据（结论：已证明）

| 环节 | 读数 | 说明 |
|---|---|---|
| 眼镜采集 | `cxr-service: AudioRecord8.pcm ... 2000 ms record 32000 samples` | 16 kHz mono、实时采集（≈16 010 samples/s） |
| CXR → 手机 | `P3_FRAME` 连续递增；`overflow=0`、`unknownFormat=0` | PCM 连续进入手机 ingress |
| 帧化 | `bytes / frames = 640 B` = 320 samples = 20 ms @16 kHz | 帧几何与 `tools/scripts/p2/engine-manifest.json`（`frameMillis=20`、`sampleRateHz=16000`）一致 |
| 内容 | `P3_ACOUSTIC Speech/Silence` + `P3_ASR` 出字 | 不是静音流；被 VAD/ASR 正常消费 |
| 注入对账 | `frames − accepted = 2 284` = 注入块数之和 | 注入音频也完整进入同一条管线 |

> 记录纪律：只保存计数/id/状态，不保存转写正文与音频；`DebugAudioInjector` 本身也只记计数与文件名。

### 5.2 2× 异常读数

- 会话 generation=4：22:41:07.544 armed → 23:14:01.407 末次汇总。
  - 墙钟：约 **1 973.9 s**。
  - 音频时长：`194 991 帧 × 20 ms = 3 899.8 s`。
  - 比值：**≈1.976（约 2×）**。
- 连续速率抽样：
  - 22:41:10.122 `frames=252`（armed 后 2.58 s）≈ 97.7 帧/秒；
  - 22:42:18.469 `frames=7086` → 22:42:21.038 `frames=7342`：Δ256 / 2.569 s ≈ 99.6 帧/秒。
- 换算字节率：100 帧/s × 640 B = **64 000 B/s**；验证格式 16 kHz mono PCM16 = **32 000 B/s** ⇒ 现场流约 **2× 验证字节率**。
- 注入期间：≈52.6 帧/秒 = **1×**。

> 说明：`P3_FRAME` 的 `accepted` 是 CXR transport 侧 offer 计数；会话 3/4 中 `accepted` 与 `frames` 在注入前相等（每 offer 恰一帧），注入才产生差值。2× 成因尚未判别：可能是回调被调用两次（重复块）、两路音频流同时投递、或采样率/声道解释与验证值不符。**本项目不记录音频内容，所以仅凭计数无法直接区分。**

## 6. 结论分级

### 6.1 已实测（可直接引用）

1. 眼镜麦克风音频连续到达手机 ingress（`P3_FRAME` 不间断、零溢出；ASR 正常出字）。
2. 现场流约为验证格式的 **2×** 实时字节率（100 帧/s × 640 B = 64 KB/s；注入 1× = 52.6 帧/s）。
3. 注入音频按 1× 完整进入管线（5 次注入、2 284 块逐块对账）。
4. 当前安装构建/进程：**5 次已知唤醒录音注入 0 命中**（`P3_WAKE=0`、`P5_CHIME=0`）。
5. 设备安装 APK 内 KWS 六个资源文件与干净构建逐文件 SHA-256 一致。
6. 现场会话 2 次（generation 3/4）中 `P3_WAKE`/`P5_CHIME`/`PANEL_*` 均为 0。

### 6.2 高置信推断（缺一条直接计数）

7. wake 检测器收到了这些帧：同一循环先 `wake.accept` 后 `pipeline.accept`，且 pipeline 对同一批帧正常产出 VAD/ASR；`WAKE_UNAVAILABLE` 未出现。⇒ 0 命中是**检测未命中**，不是"帧没到 wake"。
   - 缺口：还没有 wake 专属的 accept/emit 计数（需诊断构建，本轮未做）。

### 6.3 未确定（需要下一步取证）

8. 0 命中是"长进程/多次会话后的状态问题"还是"当前构建的回归"：未做应用重启 A/B（本轮分析未重启 App）。
9. 2× 现场流的具体机制（重复回调 / 双流 / 速率解释）未判别。
10. 业主口述"更早的初始版本上中文唤醒词可用"未在本轮复核（未找到该版本构建或当时日志）；0.24 文档中 wake PASS 均为**注入**证据（S1 门禁、S5 走查 18 次注入 8 命中），**无真人现场麦克风唤醒的正命中证据**。
11. 2× 是否影响 KWS：因为 1× 注入同样 0 命中，暂不能把 2× 当作唯一根因。
