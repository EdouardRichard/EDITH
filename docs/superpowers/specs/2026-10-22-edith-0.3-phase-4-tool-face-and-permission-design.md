### 1.3 确认交互事实

- 四个通道已有代码：Edith 内 `AlertDialog`、通知 action（`edith-confirmations-v2`）、眼镜 `Assistance` + `CONFIRM_STATE`、语音精确词。
- 非 Edith 通道存在降级/可见性缺口：
  - 通知只在会话页不可见时投递；页可见时只有对话框。
  - 通知权限/App 通知关闭时只留卡片；渠道级关闭检测不到（`available()` 只查 App 级开关）。
  - 后台弹主屏依赖 `SYSTEM_ALERT_WINDOW`；缺失时只记 `P3_CONFIRM_RAISE raised=false reason=NO_OVERLAY_PERMISSION`。

- 超时拒绝（不是自动批准）；同一时刻只允许一个确认；结算后模型重试会再次询问；无确认频率上限/冷却。
- 当前不存在任何全局/工具/会话级 bypass、silent、auto-approve、no-confirm 配置。

**工作流 B1：权限与确认**

1. 统一 atomic/umbrella 的风险级，修“同一动作 atomic L2、umbrella L1”的不一致。

5. shell 分类器误报/漏报修复；count-only 触发基线（每任务确认次数、命令类别、主动触发次数）。

## 3. 业主决定（Proposed；批准后写入 DECISIONS）

> 以下 D 编号为提议（D188 之后），实际编号以写入 DECISIONS 时为准。

### D189 — “不拦截”模式（全局、持久、默认关）

- **作用域**：全局；对所有工具、`WAKE` 与 `PROACTIVE` 两条路由、所有会话生效；不是 per-session、per-tool 或 per-turn。
- **语义**：开启后 `L0–L4` 全部不弹确认，并**绕过 `maxLevel` 上限**；`device`/`open`/`dial`/`shell` 与未来 atomic/umbrella 工具一视同仁。
- **持久化**：写入持久化设置；**App 关闭、进程被杀、设备重启都不改配置，也不自动回退**；只有用户显式关闭才退出。
- **开启**：默认 `false`；开启需要二次确认 + 风险说明（一次性设置交互）；关闭可立即生效。
- **保留**：审计（只记动作类型/风险/结果/计数，不记正文）、STOP、界面上持续状态提示；不保留逐动作确认。
- **与既有决定的关系**：仅在模式开启时 supersede **D182 的“L3/L4 永不免确认”**与 `WhitelistActionPolicy` 的硬上限；D47/D48 只在“确实需要确认”时适用，不要求每个动作都确认。旧判词不改。
- **默认行为**：模式关闭时，D182/D47/D48 与普通模式语义完全不变。

### D190 — 普通模式的“上限”与风险级统一

- `maxLevel` 改为**自动执行上限**：`risk ≤ maxLevel` 自动执行；`risk > maxLevel` 走确认（`RequireConfirmation`），不是直接 `Refuse`；L3/L4 无论上限如何都必确认（D182）；没有可用确认通道时拒绝。
- 统一 atomic/umbrella 的风险级：同一能力和同一 scope 的动作使用同一风险级。具体映射见 §4.1；目标是让默认 `maxLevel=L1` 下的核心 UI 操作（tap/long_press/input_text/scroll/open/dial）可用，同时 L3/L4 仍必确认。
- 默认 `maxLevel` 保持 `L1`；用户可在设置中调整。L2 的精确白名单语义保留。
- “UI 层不可分类的不可逆操作”（例如在别的 App 里点“删除/支付”）仍是已知残余风险；不把工具级确认宣称为覆盖所有 UI 副作用。

### D191 — 确认交互（不进入 Edith）

- 确认/拒绝至少支持一条**非 Edith**通道；优先级：眼镜自动开面板 + ENTER/BACK > 通知 action > 语音精确词；Edith 内模态框为最后兜底。
- 通道不可用时必须记录明确的降级原因；不能静默变成“只能进 Edith”。
- 120 s 窗口（D47）与可感知弹主屏（D48）只在“确实需要确认”时适用；不拦截模式不产生确认。
- 设备验收必须覆盖：手机在后台/锁屏/眼镜面板隐藏/通知权限缺失等场景。

### D192 — shell 分类器与确认

- 修 `cmd package list packages` 等良性命令误报；修 `pm disable`/`settings put`/`am force-stop` 等高风险命令静默放行。
- shell 的确认仍走命令级 precheck；不拦截模式跳过 precheck。
- 分类器硬编码白名单保持不可由用户任意扩写；用户白名单仍只用于 L2 精确 `(action, scope)`。

## 5. 工作流 B1：权限与确认

### 5.1 策略模型

- `PolicyMode = NORMAL | NO_INTERCEPTION`。
- **NORMAL**：
  1. `risk > maxLevel` → `RequireConfirmation`（D190 改变原 `Refuse`）。
  2. `requiresConfirmation=true` → `RequireConfirmation`（插件只能收紧）。
  3. `risk ≤ L1` → `Allow`。
  4. `risk == L2` → 命中精确 `(name, scope)` 白名单则 `Allow`，否则 `RequireConfirmation`。
  5. `risk ∈ {L3,L4}` → `RequireConfirmation`（D182 保持）。
  6. 无可用确认通道 → `Refuse`（明确 code）。
- **NO_INTERCEPTION**：`decide()` 恒 `Allow`，不检查 `maxLevel`、`requiresConfirmation`、白名单；shell precheck 跳过。审计记录模式。
- 策略快照：普通模式每回合开始时快照；不拦截模式是 live 全局门，在每次 `decide()` / shell precheck 时读取；设置保存后从下一次工具调用起生效，不回溯已派发的动作；不在回合中途重写普通模式的快照。
- 插件仍只能收紧；不拦截模式作为宿主级显式模式，优先于插件收紧（因为它是业主显式选择）。该优先级写入 spec 与测试。

### 5.2 风险级与 shell 分类器

- 风险映射见 §4.1；`device` 的 UI 动作与 atomic `tap`/`input` 统一 L1。
- shell 分类器修复：
  - 良性查询放行：`cmd package list packages`、`pm list`、`settings get/list`、`dumpsys`、`content query`、`am start`（现有）、`cmd package resolve-activity` 等。
  - 高风险命令确认：`pm clear/uninstall`、`content insert/update/delete`、`rm/mv/dd`、`reboot`、`input`、`am force-stop`、`pm disable`、`settings put/delete`、`su`、`kill` 等；具体表由测试钉住。
  - 未知/无法解析/复合/变量/重定向保持 fail-closed（确认）。
- 用户白名单仍只用于 L2 精确 `(action, scope)`；不能绕过 shell 命令级 precheck（除非不拦截模式开启）。

### 5.3 “不拦截”模式（D189）

- 持久化字段：`SmartSettings.noInterception: Boolean = false`（名称以实现为准）；写入 `smart-settings` blob；旧 blob 缺字段默认 `false`。
- 全局 live 门：宿主保存设置后更新进程级只读 gate；插件 `decide()` 与 shell precheck 在每次调用时读取；从下一次工具调用起生效，不回溯已派发的动作；不需要重启 App。App 关闭/被杀/重启后从持久化恢复；只有用户显式关闭才退出。
- 开启交互：设置页开关 + 二次确认对话框 + 风险说明；关闭立即生效；开启/关闭都记录 count-only `P4_POLICY` 行。
- 状态提示：App 内持续 banner；可用时通知/眼镜显示“不拦截已开启”；STOP 仍可用。
- 审计：`P4_POLICY mode=no_interception action=<name> risk=<Lx> outcome=<...>`，只记动作类型/风险/结果/计数，不记参数/正文；沿用 D117。
- 测试：L0–L4 全部 Allow；shell 危险命令不弹确认；`maxLevel` 被绕过；App 重启/force-stop 后仍为 true；用户关闭后恢复普通模式；插件 `requiresConfirmation` 不能重新拉起确认。
- 设备验收：合成文件删除（`shell rm`）在不拦截模式下无确认执行；普通模式下仍确认/拒绝；证据零正文。

### 5.4 确认通道

- **眼镜（首选）**：确认时主动 `PANEL_OPEN` + `SHOW` + `CONFIRM_STATE`；面板已隐藏时先开面板；ENTER=允许、BACK=拒绝；超时/面板关闭走 120 s 闸门；重开面板不得清空未结算确认。需要设备验证 HyperOS 上 overlay 可见性。
- **通知（次选）**：高优先级通知 + 三 action；规则：会话页可见时用对话框、页不可见时投递通知，两者不重复；修渠道级关闭检测；缺通知权限时记录 `UNAVAILABLE`。
- **语音（再次）**：只接受 ASR final 精确匹配“允许/拒绝/急停”；只对已呈现的确认生效；不做置信度猜测；语音不是唯一通道，不可用时回退通知/眼镜。
- **Edith 内模态框（兜底）**：保留；不作为唯一可用路径。
- **降级记录**：`P4_CONFIRM channel=... available=... reason=...`，只记计数/原因，不记正文。
- **120 s**：D47 单源；不拦截模式不启动计时。
- **验收**：后台/锁屏/面板隐藏/通知关闭/Settings 上层等场景至少一条非 Edith 通道可用；不能出现“只能进 Edith”。

### 5.5 触发基线与“触发概率太高”

- 新增 count-only 遥测：`P4_CONFIRM tool=<name> risk=<Lx> decision=<allow|deny|timeout|unavailable> channel=<...>`；`P4_PROACTIVE` 沿用既有主动触发日志（不新增内容）。
- 预注册一轮设备/人工场景，统计：每任务确认次数、按工具/命令类别分布、主动触发次数、每任务工具调用数；不记正文。
- 用途：确认“触发概率太高”是 shell 误报、主动触发、还是 24 工具接入后的 L2–L4 确认；为阈值与默认值提供基线。没有读数就写 `NotMeasured`，不预设数字。
- 基线不阻塞实现；但 spec 的默认值（L1、不拦截默认关）按当前事实先定，基线结果若需改默认值，另立决定。

### 5.6 验收

- 普通模式：L3/L4 确认率 100%；>上限得到确认；无通道时拒绝；白名单精确命中；插件收紧生效。
- 不拦截模式：L0–L4 全部 0 确认；绕过上限；App 重启/被杀后仍生效；审计/STOP 可用；关闭后恢复普通模式。
- 通道：至少一条非 Edith 通道完成 allow 与 deny；降级原因可见；无“只能进 Edith”。
- shell：良性命令不误报；高风险命令确认；不拦截模式跳过 precheck。

## 9. 风险与未验证项

1. **不拦截的安全风险**：开启后不可逆动作（卸载/清数据/权限变更/`rm`）无确认；缓解只有默认关、显式开启、审计、STOP、状态提示。业主 2026-10-22 批准该模式时已确认此风险；实现验收必须保持默认关与显式开启。
2. **D182 的 supersede 边界**：只在模式开启时生效；普通模式保持 L3/L4 必确认。旧判词不改，但新增验收行必须区分模式，避免把“不拦截 0 确认”误读成普通模式通过。
3. **风险级统一**：把 atomic tap/input 从 L2 降到 L1 需要确认不会削弱安全边界；`device` 已 L1 是主要理由；UI 层不可分类的不可逆操作仍是残余风险。
4. **确认通道平台限制**：HyperOS 后台弹窗、通知渠道、眼镜 overlay、Settings 上层都可能降级；任何一条通道“JVM 通过”不等于设备可用。
5. **24 工具选择负担**：atomic + umbrella 并存会让模型选错；需要描述/路由测试与延迟矩阵证明；没有矩阵不声称“保延迟”。
6. **旧语料**：27 行重跑是 Phase 4 范围，但旧判词不改；新读数并列；`NotMeasured` 不读成通过。
7. **设置 live 语义**：不拦截模式是“配置一次全局生效”的持久化 live gate；从下一次工具调用起生效，不回溯已派发动作，不在回合中途重写普通模式快照。该语义写入测试与验收。
8. **App 关闭不改配置**：必须用持久化测试 + force-stop/重启设备验证；不能只靠进程内单例。
9. **构建 provenance**：Phase 4 设备证据必须重新声明 build/APK hash；不能沿用 `8d075f40` 的旧读数。
10. **UI 层不可分类的不可逆操作**：工具级确认不覆盖别家 App 内的“删除/支付”；这是已知残余，不宣称解决。
