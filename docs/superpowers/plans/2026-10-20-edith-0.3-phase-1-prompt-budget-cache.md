# EDITH 0.3 Phase 1 — Prompt, Budget, Cache, Telemetry Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use subagent-driven-development (recommended) or executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Replace EDITH's hardcoded prompt and fixed 4K budget with a device-sourced, versioned prompt catalog, a profile-driven token budget, a cache-stable request layout (dynamic tail), and cache/prompt telemetry — all proven on the JVM before any device run.

**Architecture:** The plugin owns prompt content (`PromptCatalog` resources) and the base runtime owns only mechanism (`TurnPolicy`/`RequestLayout`/`ContextPolicy`/`TokenMeter`). The system slot is static per session; memory/perception/skill bodies move to a request-scoped dynamic tail; summary stays at the history head. All budget sizes come from the user's `ModelProfile`; no fixed 4096/8192/1M constants.

**Tech Stack:** Kotlin/JVM, Gradle, kotlin.test/JUnit5, kotlinx.serialization; Android only for the `DeviceProfile` provider (JVM-testable through injected lambdas).

**Spec:** `docs/superpowers/specs/2026-10-20-edith-0.3-harness-design.md` — read §3–§6 and §9.4 before starting.

**Phase boundary:** This plan is Phase 1 only. Phase 2 (perception providers/snapshot/ref), Phase 3 (proactive follow-up), and Phase 4 (tool surface/norms/acceptance) get separate plans. Do not implement them here. Phase 1 has no device tests; device latency/cache readings are Phase 4. Phase 1 also does **not** implement the structured compression summary, `ProfileForm` new-profile defaults/validation, or the full production-source hardcode scan; those are Phase 4 norm work. Phase 1 uses existing configured profiles and fails closed when a profile is invalid.

---

## Global Constraints

- Branch `feat/0.3-harness`; **no push, tag, or merge**. Commit after each task.
- **No fixed budget constants**: budget sizes come from `ModelProfile`; policy ratios/counts are tuning, not token sizes.
- **No prompt text in Kotlin production sources**: prompt prose lives only in `plugin-smart-helper/src/main/resources/prompts/`; generic loop prose lives only in `agent-runtime/src/main/resources/prompts/loop/`.
- System prompt contains only `STATIC`/`SESSION_STATIC`/pinned content. Current time, foreground, media, battery, memory, perception, skill bodies go in the request-scoped dynamic tail.
- Do not put `MEMORY_EVIDENCE`/`PERCEPTION`/`SKILL_BODY` into `history[0]`; summary may stay at the history head.
- Preserve the old `P3_METRIC` line shape; add `P3_PROMPT`/`P3_CACHE` as separate count-only lines.
- Logs/evidence never carry prompt text, transcript text, or device content; only counts/IDs/hashes/version.
- 0.25/0.26 acceptance verdicts are unchanged; Phase 1 claims only JVM results.
- Use the shared `TokenMeter`; do not introduce a second token estimator.
- `ImageBudget.UNITS_PER_IMAGE` stays the single image cost unit shared by `ContextBudgeter` and `TurnTrimmer`.
- Device facts come from `DeviceStateProvider`; missing fields stay null and are omitted from the prompt, never defaulted.
- Run commands from the repo root with `.\gradlew.bat` on Windows.

## Review Focus

These are the failure modes a reasonable user would hit; each gets a test in the task that owns the code:

1. **Missing device fields** (glasses model/firmware null, capability absent) must be omitted from the prompt, not rendered as `unknown`/default values.
2. **Invalid or too-small `ModelProfile`** must fail closed (`PROFILE_INVALID`/`PROFILE_TOO_SMALL`), never fall back to a hidden default budget.
3. **Dynamic time/foreground/memory changes** must leave the system text and history prefix byte-stable; only the dynamic tail changes.
4. **Memory/perception/skill bodies** must not be folded into `history[0]`; summary remains the only context at the head, or AC-1/AC-3 regress silently.
5. **TokenMeter migration** must not let an over-budget request through: a profile that fit under the old byte accounting must still fit; a request over the profile limit must still be rejected/trimmed.

**Interfaces:**
- Produces:
  ```kotlin
  object TokenMeter {
      fun estimate(text: String): Int
  }

  data class ContextTuning(
      val compressionThreshold: Double = 0.75,
      val hardMarginRatio: Double = 0.10,
      val keepRecentTurns: Int = 4,
      val summaryRatio: Double = 0.02,
      val toolResultRetention: Int = 4,
  )

  data class ContextPolicy(
      val hardInputLimit: Int,
      val softLimit: Int,
      val hardLimit: Int,
      val compressionThreshold: Double,
      val hardMargin: Int,
      val keepRecentTurns: Int,
      val summaryMaxTokens: Int,
      val toolResultRetention: Int,
  ) {
      companion object {
          fun from(profile: ModelProfile, tuning: ContextTuning = ContextTuning()): ContextPolicy
      }
  }
  ```
- `TokenMeter.estimate`: empty → 0; CJK code points (CJK Unified, Hiragana/Katakana, Hangul) count 1; ASCII count 1/4; other code points count 1; return `max(1, ceil(sum))`.
- `ContextPolicy.from`: `hardInputLimit = min(profile.inputBudgetTokens, profile.usableWindowTokens - profile.maxOutputTokens - profile.safetyTokens)`; `softLimit = floor(hardInputLimit * compressionThreshold)`; `hardMargin = max(1, floor(hardInputLimit * hardMarginRatio))`; `hardLimit = hardInputLimit - hardMargin`; `summaryMaxTokens = max(1, ceil(hardInputLimit * summaryRatio))`; validate `0 < softLimit <= hardLimit <= hardInputLimit`, threshold in `(0,1)`, `keepRecentTurns >= 1`, `summaryMaxTokens > 0`.
