## 2. 通用启动提示词（复制即用）

把 `{{PHASE}}` 替换为本次阶段（`P0`…`P6`），一个会话只执行一个 Phase。

```text
你是 EDITH 0.23 的 Phase {{PHASE}} Agent。工作目录：D:\Project_new\EDITH。

本提示词只负责启动。本阶段的规格、需求、范围、依赖、验收、进度与上一阶段交接，全部从文档读取；本提示词不复述、也不作为任何判据。若提示词与文档冲突，以文档为准。

【开工顺序】
1. 读 AGENTS.md（项目约束、铁律、设备纪律）。
2. 读 docs/project/STATUS.md：当前 checkpoint、下一动作、上一阶段交接、未测项。
3. 读 docs/superpowers/specs/2026-10-17-edith-0.23-requirements-and-phase-division.md：需求与阶段划分。
4. 读 STATUS 指向的 P0 批准版规格与计划；从其中找到 Phase {{PHASE}} 的任务、作用域、依赖与验收。
5. 读本阶段相关的 ACCEPTANCE / DECISIONS / CONTRACTS / evidence（由 STATUS、规格、计划指向）。
6. 涉及官方 UI/交互时，读 D:\Project_new\rokid_glasses_UI 的对应文件；涉及眼镜/手机互联时，先读 D:\Project_new\rokid-glass3-sdk-skill\SKILL.md 再按其路由读参考。
7. .local/0.23-candidate.patch 只作参考；不得把其中任何写法当作已批准实现。

【接续检查（先报告，再动手）】
- 核对 git branch/HEAD/status 与工作树；记录未提交改动。
- 确认文档中 Phase {{PHASE}} 的前置阶段已完成且已批准；若未完成、未批准或文档缺失，停止并报告"上一阶段未完成/文档缺失"，不要补做、不要跳阶段。
- 不要依赖上一会话的聊天记录；以 STATUS、规格、计划、evidence 为准。
- 输出 5 行接续确认：当前 Phase / 已批准基线 / 上一阶段产物 / 未测项 / 本阶段第一动作。

【流程】
1. 加载 skill: using-superpowers；涉及需求/设计时加载 brainstorming。
2. 需求、设计、规格、计划的审阅门按文档规定执行；需要业主确认的，停下来等待，不自行批准。
3. 开发执行按文档与批准计划进行；编码使用 test-driven-development；完成前使用 verification-before-completion。
4. 证据先于结论；未测写 NotMeasured，不把 JVM/代码通过写成设备通过。
5. 结束只更新文档（STATUS、ACCEPTANCE、evidence、计划勾选等），不自动进入下一阶段。
6. 在 STATUS 留下本阶段 checkpoint 与给下一阶段的交接；交接格式以文档规定为准。

【边界】
- 本提示词不定义任何规格、需求、进度或禁止项；这些一律以文档为准。
- 不擅自 push / commit / tag / 合并；需要授权时先问。
- 设备与安全纪律以 AGENTS.md 为准。
```

## 3. 各 Phase 的启动参数

粘贴上面的通用提示词，替换 `{{PHASE}}` 即可。本阶段的具体内容**不在本表**，在文档中：

| P0 | `{{PHASE}}` → `P0` | 需求文档 §5 的 P0；STATUS 的"下一动作" |

## 4. 使用规则

1. **一个 Phase 一个新会话**；不要在同一会话里连续跨阶段执行。
2. 提示词只启动；**范围、验收、依赖、进度、上一阶段交接**都从 `STATUS.md` 与 P0 批准版文档读取。
3. P0 必须由业主参与澄清与规格/计划审阅；P1–P5 的计划批准后，开发执行可无人值守；P5 的线缆变更仍需业主批准契约。
4. 任何只有代码/JVM 证据的行只能写 `Verified (JVM)`；设备半边未测写 `NotMeasured`。
5. 结束必须更新 STATUS；下一会话从 STATUS 接续，不从聊天记录接续。
